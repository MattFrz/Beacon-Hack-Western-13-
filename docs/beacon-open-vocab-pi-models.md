# Research: Open-vocabulary / zero-shot visual labeling on Raspberry Pi 5 (8 GB, CPU only) for Beacon

Background for `docs/nathans-revision.md`. Detector pick (YOLOE-26n baked ONNX) is locked in that file.


## Summary

Only one family has both (a) real open-vocabulary labeling from text and (b) a plausible Pi 5 CPU budget alongside depth, VO, MediaPipe hands and 60 Hz audio: **Ultralytics YOLOE-26n** exported to **static ONNX with a small baked prompt set**, run on QNX's packaged **onnxruntime 1.24.4**. Pi 5 numbers are Linux proxies (vendor doc says ~3–5 FPS at 320 px for the nano model); no QNX measurement exists, so the Saturday decision must be validated with one p50/p95 run on the loaner. Keep the POI store as **label string + 3D centroid + timestamp**, and do query-time "refill water" → "fountain / water bottle / sink" remapping with a deterministic synonym table first and, only if needed, the already-available QNX `llama.cpp` with a 0.5 B GGUF. Do **not** add a CLIP crop index or a vision-language model this weekend; measured Pi 5 costs are 200 ms+ for a single CLIP encode and seconds-to-tens-of-seconds for VLMs.

## Findings

1. **YOLOE-26n (text-prompted, ONNX) is the most defensible Saturday candidate.** It is a YOLO-shaped detector whose class semantics come from prompts; after export the prompt embeddings are folded into a normal YOLO head, so the runtime sees ordinary ONNX inference with no text encoder. Released checkpoint `yoloe-26n-seg.pt` is 11.2 MB; paper-config params/FLOPs are 3.9 M / 6.1 B (the released seg checkpoint carries extra mask/text-projection branches) ([Ultralytics YOLOE docs](https://docs.ultralytics.com/models/yoloe), [Ultralytics assets v8.4.0](https://github.com/ultralytics/assets/releases/tag/v8.4.0)). Export supports ONNX and LiteRT, and prompt embeddings can be saved once (a 3-class profile was 6,436 bytes on one x86 test) and baked into the model so the 254 MB `mobileclip2_b.ts` encoder never has to ship to the Pi ([Ultralytics YOLOE docs](https://docs.ultralytics.com/models/yoloe), [NerdlyBuilds CPU test](https://nerdlybuilds.com/blog/yoloe-text-prompts-tested/)). Measured latency: a Sunfounder Pi 5 guide claims ~3–5 FPS at 320 px for the nano model (≈200–333 ms/frame), but gives no methodology ([Sunfounder docs](https://docs.sunfounder.com/projects/ai-lab-kit/en/latest/yolo/yolo_yoloe.html)); on a 2-vCPU x86 cloud box with three prompts, nano PyTorch measured 85–90 ms/image ([NerdlyBuilds](https://nerdlybuilds.com/blog/yoloe-text-prompts-tested/)). Nearby Pi 5 anchors: YOLO26n ONNX 128.42 ms at 640 px and YOLO26n NCNN 67.03 ms at 640 px, both inference-only, Linux ([Ultralytics Pi guide](https://docs.ultralytics.com/guides/raspberry-pi)). QNX-feasibility: **proxy-Linux / QNX yes** — ORT is packaged (`onnxruntime` 1.24.4 per user-confirmed catalog; QNX lists ORT as a core inference runtime), but export must happen on an x86/macOS host because Ultralytics LiteRT export explicitly refuses Linux ARM64 ([QNX Physical AI blog](https://qnx.software/en/blog/2026/how-qnx-gives-developers-the-building-blocks-for-physical-ai), [Ultralytics LiteRT docs](https://docs.ultralytics.com/integrations/litert)). License: **AGPL-3.0** for Ultralytics weights/code; an embedded commercial product needs an Enterprise licence ([Ultralytics licence](https://www.ultralytics.com/license)). Open-vocab: yes at prompt/export time, **fixed vocabulary at runtime** unless you re-export.

2. **YOLOE-26n prompt-free (`yoloe-26n-seg-pf.pt`) is the only realistic "label anything we walk past" variant.** It answers from a built-in 4,585-name vocabulary with no prompt and no text encoder; checkpoint is 15.5 MB and the paper-config model is 2.3 M params / 5.3 B FLOPs ([Ultralytics YOLOE docs](https://docs.ultralytics.com/models/yoloe), [Ultralytics assets](https://github.com/ultralytics/assets/releases/tag/v8.4.0)). Caveats: LVIS minival mAP is only 16.6–17.7, and the region-text comparison against the full vocabulary adds about **89% forward-pass time on CPU** at `yoloe-26s-seg` (80 → 4,585 names: +19% at 1,203); FLOPs counts do not show this ([Ultralytics YOLOE docs](https://docs.ultralytics.com/models/yoloe)). No Pi 5 latency for the pf checkpoint was found. QNX-feasibility: **proxy-Linux / QNX yes** via the same ONNX path. License: AGPL-3.0 ([Ultralytics licence](https://www.ultralytics.com/license)). Open-vocab: yes, cataloguer-style, at runtime.

3. **YOLO-Worldv2-s ONNX is viable but strictly worse than YOLOE for this budget.** `yolov8s-worldv2.pt` is 24.7 MB and only the `worldv2` weights export to ONNX; the original `*-world` weights do not ([Ultralytics YOLO-World docs](https://docs.ultralytics.com/models/yolo-world), [Ultralytics assets v8.2.0](https://github.com/ultralytics/assets/releases/tag/v8.2.0)). Official export requires re-running `--custom-text` to change prompts, so runtime classes are also fixed ([YOLO-World deploy docs](https://github.com/AILab-CVC/YOLO-World/blob/master/docs/deploy.md)). Pi 5 evidence: a Core Electronics tutorial actually runs `yolov8s-world.pt` at 640 px on a Pi 5 in PyTorch but publishes **no timing**, says it is "much slower" than closed-set YOLO, and notes it cannot be converted to NCNN ([Core Electronics](https://core-electronics.com.au/guides/getting-started-with-yolo-object-and-animal-recognition-on-the-raspberry-pi/)). The only hard detector number found is 26.07 ms for YOLO-World-S in PyTorch on a **Jetson AGX Orin GPU**, not Pi CPU ([Frontiers 2025](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2025.1693988/full)). License: GPL-3.0 upstream / AGPL-3.0 if loaded via Ultralytics ([YOLO-World repo](https://github.com/AILab-CVC/YOLO-World?tab=readme-ov-file), [Roboflow model licences](https://docs.roboflow.com/models/model-licenses)). QNX-feasibility: **proxy-Linux / QNX yes** via ORT, but unknown Pi timing makes it a fallback, not the pick.

4. **YOLO-World INT8 TFLite is a credible speed play, not a weekend shortcut.** The authors ship a documented ONNX → `onnx2tf` INT8 path for reparameterized YOLO-World, requiring ~100 calibration images and dropping `bbox_decoder` from the ONNX graph; reported accuracy loss is ~1.0 AP on COCO, and the text encoder is not quantized ([YOLO-World TFLite docs](https://github.com/AILab-CVC/YOLO-World/blob/master/docs/tflite_deploy.md), [issue #339](https://github.com/AILab-CVC/YOLO-World/issues/339)). QNX ships `tflite-runtime` 2.21.0, so runtime availability is not the blocker ([QNX research notes in repo](https://oss.qnx.com/)); export must be done off-target. Existing QNX TFLite projects warn that packaged C++ FlatBuffers headers and `libtensorflow-lite.so` minor versions mismatch, recommending the stable C API ([QNX ai-camera repo](https://github.com/mghanem4/ai_camera_raspberry_pi)). No Pi 5 INT8 latency was found. Treat as **bench experiment**, not the Saturday path.

5. **CLIP-style retrieval costs as much as another detector and should stay off the hot loop.** On a Pi 5 CPU in PyTorch, CLIP ViT-B/32 encode was 262.6–264.7 ms/image and MobileCLIP2-S0 200.3–206.9 ms/image (smaller resolutions, still ~200 ms) ([arXiv 2610.05764](https://arxiv.org/abs/2610.05764)). An ONNX MobileCLIP2-S0 card reports 112 ms vision encode on an unspecified CPU and 1,393 ms for full dynamic INT8 ([HF card](https://huggingface.co/felixhrdyn/mobileclip2-s0-onnx)); Arm's INT8 CLIP ViT-B/32 ExecuTorch model measures 95.5 ms p50 on Pi 5, but ExecuTorch is **not** a QNX package ([Arm HF card](https://huggingface.co/Arm/clip-vit-base-patch32-int8-xnnpack-executorch), [QNX Physical AI blog](https://qnx.software/en/blog/2026/how-qnx-gives-developers-the-building-blocks-for-physical-ai)). CLIPSeg-style open-vocab segmentation on Pi 5 CPU ran at 0.02–0.17 Hz ([BlabberSeg paper](https://arxiv.org/abs/2410.12979)). FastSAM's text-to-mask path explicitly feeds every mask crop through CLIP and is called "not satisfying"; FastSAM-s alone took ~13.7 s/image on Pi Zero 2W PyTorch ([FastSAM paper](https://arxiv.org/abs/2306.12156), [pi-sam repo](https://github.com/ravijo/pi-sam)). QNX-feasibility for plain ONNX CLIP: yes; for the fast ExecuTorch variant: no.

6. **Retrieval: label + query remap is enough for a small session-scoped POI store; a CLIP/vector index is not justified.** Prior systems bridge natural language to structured 3D data with an LLM or explicit query rewriting before similarity search: NLMap uses few-shot LLM "object proposal" because bridging unstructured instructions to scene representation is "the core challenge" ([NLMap](https://arxiv.org/abs/2209.09874)); Embedding Pose Graph says the query is extracted from the user command with prompt-engineered LLM before cosine matching ([EPG](https://arxiv.org/html/2403.13777v1)); KeySG decomposes queries into entities and embeds text chunks in FAISS ([KeySG](https://arxiv.org/html/2510.01049)). Conversely, LOST-3DSG deliberately avoids dense CLIP features: object-level labels + word2vec/sentence embeddings + 3D boxes used ~3 KB where per-voxel CLIP features would need ~641 MB ([LOST-3DSG](https://arxiv.org/html/2601.02905)). Affordance queries like "I need to know the time" → clock have been shown, but via CLIP/DINO language fields baked into NeRF, which is far outside this weekend's runtime ([3D QSR / LERF discussion](https://arxiv.org/html/2509.20077)). Practical Beacon shape: store `{label, xyz, t, conf}`; `voiced` maps "refill water" → candidate labels `water fountain | fountain | water dispenser | sink | bottle` with a table first, and a tiny text-only LLM only as fallback. A 0.5 B Qwen2.5 GGUF runs at roughly 12–34 tok/s on Pi 5 CPU with 0.27–0.44 s TTFT in published tests, i.e. ~1–2 s for a 16-token remap, off the hot loop ([ggml discussion #30069](https://github.com/ggml-org/llama.cpp/discussions/30069), [Jurnal ELTEK](https://doi.org/10.33795/eltek.v24i2.11288), [ai-tier](https://ai-tier.com/results/raspberry-pi-5/qwen2-5-0-5b-instruct/)); llama.cpp is a real QNX port (`b8808` tested, CPU-only ggml) ([llama.cpp-qnx](https://github.com/xtang2010/llama.cpp-qnx)). Note the remap quality itself is untested for this phrase pair.

7. **QNX packaging narrows the runtime choice.** QNX's own AI-package roundup lists ONNX Runtime and PyTorch/OpenVINO as cross-compile-only, MediaPipe, OpenCV and TFLite as ported; it does **not** list NCNN, ExecuTorch, TensorRT or RKNN ([QNX Physical AI blog](https://qnx.software/en/blog/2026/how-qnx-gives-developers-the-building-blocks-for-physical-ai), [qnx-ports/build-files](https://github.com/qnx-ports/build-files)). `onnxruntime` was also built for QNX historically only with manual patches ([ORT issue #12267](https://github.com/microsoft/onnxruntime/issues/12267)), so even a packaged version deserves an early smoke test on the loaner. Ultralytics' own Pi guide calls NCNN fastest on ARM, but that is a Linux-only option here; ONNX is the fastest documented format that is actually on QNX ([Ultralytics Pi guide](https://docs.ultralytics.com/guides/raspberry-pi), [Ultralytics blog](https://www.ultralytics.com/blog/raspberry-pi-object-detection)). Host-side export from a laptop is required for both ONNX and LiteRT ([Ultralytics LiteRT docs](https://docs.ultralytics.com/integrations/litert)).

## Explicit "do not attempt this weekend"

- **Grounding DINO full/tiny**: ORT CPU on a Jetson AGX Orin took 13,580 ms at 1200×800; OpenVINO on the same board took 102,720 ms ([arXiv 2607.11356](https://arxiv.org/abs/2607.11356)). A C++ ORT report documents complex `ScatterND`/attention operators, 6 s latencies, and graph-optimization crashes ([HackerNoon](https://hackernoon.com/dino-in-the-machine-surviving-the-transformer-latency-trap-in-c)). Grounding DINO 1.5/1.6 Edge are API-only ([hivebook summary](https://hivebook.wiki/wiki/grounding-dino-text-prompted-open-set-object-detection)).
- **DINO-X / DINO-X Edge**: 20.1 FPS is TensorRT FP16 on an **Orin NX**, and maintainers said in 2025 there are no plans to open-source the Edge model ([DINO-X paper](https://arxiv.org/html/2411.14347v3), [maintainer reply](https://github.com/IDEA-Research/DINO-X-API/issues/23)). API-only means cloud, which the prize rejects.
- **Florence-2 base**: Pi 5 PyTorch object detection 20.9–40.8 s, captions 16–17 s, >5 GB RAM and ~80 °C ([Harvard edge lab](https://harvard-edge.github.io/cs249r_book_dev/kits/contents/raspi/vlm/vlm.html), [community Pi 5 run](https://github.com/kshipra-jadav/florence2-cpu)).
- **Moondream 2B / 0.5B**: Pi 5 image encode 18.61 s (2B) / 8.75 s (0.5B), ~7 GB RAM with desktop ([Core Electronics](https://core-electronics.com.au/guides/getting-started-with-moondream-on-the-pi-5-human-like-computer-vision/)).
- **Qwen2-VL 2B / any multimodal GGUF in the frame loop**: Pi 5 CPU llama.cpp prefill 2.66 s with image, 5.92 tok/s decode, 98% host CPU, thermal throttling after 14–17 min and 24% decode loss ([energy study](https://arxiv.org/html/2610.20136)).
- **NanoOWL / OWLv2 TensorRT / anything CUDA**: NanoOWL requires Jetson TensorRT engines and `torch2trt` ([NVIDIA NanoOWL](https://github.com/nvidia-ai-iot/nanoowl/)); there is no CUDA on the Pi.
- **LingBot-Map / Cactus Mirage**: LingBot-Map requires CUDA 12.8 PyTorch + FlashInfer/Kaolin and is aimed at NVIDIA machines ([Robbyant docs](https://docs.robbyant.com/models/lingbot-map/quick-start/), [launcher](https://github.com/cocktailpeanut/lingbot-map.pinokio)); Cactus ships `linux-arm64` but not QNX targets ([Cactus platform list](https://cactuscompute.com/blog/needle-supported-devices), [HF releases](https://huggingface.co/Cactus-Compute/cactus)).
- **CLIP/vector database or affordance NeRF/Gaussian fields in v1**: 200 ms+ per encode, no QNX-ported fast runtime, and the research systems that do this use desktop-class hardware or server embeddings ([MobileCLIP Pi numbers](https://arxiv.org/abs/2610.05764), [3D QSR](https://arxiv.org/html/2509.20077), [FAISS+RAG scene graphs](https://arxiv.org/html/2510.01049)).
- **NCNN / ExecuTorch on QNX**: not in the documented QNX port set; a weekend port is not credible ([QNX blog](https://qnx.software/en/blog/2026/how-qnx-gives-developers-the-building-blocks-for-physical-ai)).

## Recommendations

- **Saturday pick:** `yoloe-26n-seg.pt` with ~16–32 text prompts chosen before the walk (keys/key fob, cup, bottle, water fountain, water dispenser, sink, phone, wallet, bag, chair, door…), prompt embeddings saved and exported once to static ONNX at 320 px on a laptop, loaded by QNX ORT 1.24.4 in `percept`. Store label strings and 3D centroids only. Add a deterministic synonym map in `voiced`; add `llama.cpp` + Qwen2.5-0.5B Q4 GGUF only as a fallback remap, capped at ~16 output tokens and strictly text-to-text. This is the only stack with a measured Pi 5-family latency that still leaves a plausible slot for 120 ms depth and a separate high-priority audio process. "Open vocabulary" here means prompt-defined labels without retraining, not arbitrary new nouns at runtime; say that plainly in the demo script.
- **Stretch if Phase 3 (VO + depth + REACH ticks + RETURN) is already green:** switch the same checkpoint slot to `yoloe-26n-seg-pf.pt` (prompt-free, no re-export to add nouns). Accepted only if the loaner measurement shows p95 still fits the cadence; the +89% CPU region-text cost at full vocabulary is the risk ([Ultralytics docs](https://docs.ultralytics.com/models/yoloe)).
- **If tied between YOLOE-26n text and YOLOE-26n-pf, the deciding loaner measurement is:** on QNX ORT with camera, depth, VO and the 60 Hz audio thread running, record p50/p95 end-to-end detector time at 320 px over 200 frames and the number of correct labels out of 10 held-up demo objects, first with 32 prompts, then prompt-free. Ship the variant whose p95 fits the remaining frame budget with ≥8/10 correct labels; do not decide from Linux FPS claims.
- **Budget honesty:** the user-supplied QNX baseline is YOLO11n ONNX 320 px ≈168 ms plus depth ≈120 ms; everything above is additive. No stack in this brief gives you a second free 200 ms CLIP pass.

## Open questions (unknown without the loaner Pi)

- Absolute and p95 latency of YOLOE-26n ONNX under **QNX ORT 1.24.4** at 256/320 px, with NEON/KleidiAI dispatch and four threads, while `guided` runs on core 0. Published numbers are Linux and often inference-only.
- Whether the exported YOLOE ONNX graph loads without missing ops in QNX ORT 1.24.4 and whether the Python binding is usable in `percept` or a C++ wrapper is needed.
- Thermal steady state after 10–20 minutes with detector + depth + VO + hands; Pi 5 VLM work shows throttling at ~83–86 °C with 24% slowdown, and the design notes require an active cooler ([energy study](https://arxiv.org/html/2610.20136)).
- Whether a 0.5 B GGUF remap actually maps "where can I refill water" to the label you stored, and its QNX latency with the rest of the pipeline loaded. No benchmark for that phrase pair was found.
- Whether the prompt-free checkpoint's region-text overhead on QNX CPU is closer to +19% or +89% for your prompt count; the published figure is for `yoloe-26s-seg` on CPU, not the nano model.
- Real depth scale / unprojection accuracy for the demo objects, and whether MediaPipe hands plus the open-vocab pass can coexist without missing the 16 ms `guided` deadline.
- Licence acceptability: AGPL-3.0 for the whole hackathon build, or an Enterprise licence, if anything is commercial or closed-source ([Ultralytics licence](https://www.ultralytics.com/license)).
